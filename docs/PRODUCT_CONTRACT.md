# Product contract v0.3 — месячный перенос 79.x

## 1. Назначение

Сервис читает ОСВ на конец месяца по точным счетам `79.2` и `79.3`, формирует журнал проводок и файлы операции МСФО. Для каждой исходной аналитической строки ненулевой конечный остаток на 79.2/79.3 полностью обнуляется в исходной организации и симметрично отражается в управляющей компании `ГК` через счет `79.1`.

Версия 1 только рассчитывает, контролирует и экспортирует файлы. Автоматическая запись в 1С запрещена.

## 2. Источники данных

1. ОСВ по `79.2`/`79.3` — источник суммы, стороны конечного сальдо, исходной организации, ЦФО и `Поставщик РВП`.
2. Иерархия организаций ERP — reference/валидация организаций и ЦФО, в том числе `ГК` и `Б_ГК Финансовый отдел`.
3. План счетов ERP — reference структуры счетов `79.1`, `79.2`, `79.3`.
4. HAT handoff владельца — reference только для формата выходной операции `Загрузка_A_AA` из 27 колонок. Бизнес-алгоритм HAT не переносится.

Реальные бухгалтерские XLSX/MXL запрещено коммитить в Git. В tests используются только синтетические fixtures.

## 3. Фактическая форма ОСВ, которую должна поддержать v1

Типовой вход — выгрузка 1С с многоуровневой группировкой в первом столбце:

- строка счета (`79.2` или `79.3`);
- строка организации;
- строка ЦФО/подразделения;
- строка `Поставщик РВП`;
- технические строки показателей `ОВ`/`ФВ`.

Заголовки показывают `Сальдо на конец периода` с отдельными колонками Дебет/Кредит. Парсер обязан восстанавливать контекст уровней и создавать нормализованные строки только с уровня аналитики `Поставщик РВП`; итоги счета/организации/ЦФО не должны повторно превращаться в финансовые строки.

Пустая аналитика не должна молча отбрасываться: она либо сохраняется как явно пустое значение, если контракт допускает это поле, либо получает BLOCKED с причиной. Нельзя угадывать значение.

## 4. Нормализованная входная строка

- `period_end`
- `organization`
- `source_account` — строго `79.2` или `79.3`
- `department`
- `supplier_rvp`
- `ending_debit`
- `ending_credit`
- `source_excel_row_ref`

Правила:

- `Decimal`, не float;
- отрицательные/служебные представления нормализуются явно и тестируются;
- нулевой остаток = `NO_ACTION`;
- после нормализации ровно одна сторона должна быть ненулевой; одновременный ненулевой Дт и Кт = `BLOCKED_INVALID_ENDING_BALANCE`;
- одна исходная аналитическая строка потребляется не более одного раза.

## 5. Утвержденная универсальная логика

Логика одинакова для `79.2` и `79.3`.

### 5.1. Конечный остаток Дт

Для INPUT:

- организация = `ORG`
- исходный счет = `79.x`
- ЦФО = `DEP`
- поставщик = `SUP`
- конечное Дт = `AMOUNT`

создать ровно две PostingRow.

**Документ исходной организации `ORG`:**

- Дт `79.1`, ЦФО `DEP`, Поставщик РВП `ГК`;
- Кт `79.x`, ЦФО `DEP`, Поставщик РВП `SUP`;
- сумма `AMOUNT`.

**Документ организации `ГК`:**

- Дт `79.1`, ЦФО `Б_ГК Финансовый отдел`, Поставщик РВП `ORG`;
- Кт `79.1`, ЦФО `Б_ГК Финансовый отдел`, Поставщик РВП `SUP`;
- сумма `AMOUNT`.

### 5.2. Конечный остаток Кт — утвержденная зеркальная логика

Для того же INPUT с конечным Кт = `AMOUNT` стороны меняются зеркально.

**Документ исходной организации `ORG`:**

- Дт `79.x`, ЦФО `DEP`, Поставщик РВП `SUP`;
- Кт `79.1`, ЦФО `DEP`, Поставщик РВП `ГК`;
- сумма `AMOUNT`.

**Документ организации `ГК`:**

- Дт `79.1`, ЦФО `Б_ГК Финансовый отдел`, Поставщик РВП `SUP`;
- Кт `79.1`, ЦФО `Б_ГК Финансовый отдел`, Поставщик РВП `ORG`;
- сумма `AMOUNT`.

## 6. Обязательные golden cases

В `tests/golden/` утверждены четыре базовых сценария:

- `DEBIT_79_2_AT`
- `CREDIT_79_2_AT`
- `DEBIT_79_3_AT`
- `CREDIT_79_3_AT`

Ни один рефакторинг не имеет права менять их результат без новой версии контракта и явного owner decision.

## 7. Контроль экономического эффекта

Для каждой исходной строки сервис обязан доказать:

- конечный остаток исходной аналитики по 79.2/79.3 после сгенерированной строки становится 0;
- в исходной организации сумма переносится на 79.1 с аналитикой `ГК`;
- в ГК создается равновеликая внутренняя проводка 79.1/79.1;
- сумма source-org PostingRow = сумма GK PostingRow;
- направление соответствует стороне исходного конечного сальдо;
- нет дублирования исходной строки.

## 8. Выходной стандарт операции МСФО

Лист называется строго `Загрузка_A_AA` и содержит ровно 27 колонок в следующем порядке:

1. `СчетДт`
2. `СчетКт`
3. `ВалютаДт`
4. `ВалютаКт`
5. `ВидОперации`
6. `ПодразделениеДт`
7. `ПодразделениеКт`
8. `НаправлениеДеятельностиДт`
9. `НаправлениеДеятельностиКт`
10. `СуммаВВалютеУчета`
11. `СуммаВВалютеОтчетности`
12. `СуммаВВалютеДт`
13. `СуммаВВалютеКт`
14. `КоличествоДт`
15. `КоличествоКт`
16. `Содержание`
17. `СчетДтИсточник`
18. `СчетКтИсточник`
19. `ИдентификаторФинЗаписи`
20. `ПравилоДт`
21. `ПравилоКт`
22. `СубконтоДт1`
23. `СубконтоДт2`
24. `СубконтоДт3`
25. `СубконтоКт1`
26. `СубконтоКт2`
27. `СубконтоКт3`

Один экспортный файл = одна дата документа + одна организация документа. Строки исходных компаний и строки ГК поэтому раскладываются в разные файлы. В import-файле нет вспомогательных листов.

Базовое отображение:

- `СчетДт`/`СчетКт` — из PostingRow;
- `ПодразделениеДт`/`ПодразделениеКт` — из PostingRow;
- `СубконтоДт1`/`СубконтоКт1` — `Поставщик РВП` соответствующей стороны;
- `СуммаВВалютеУчета` — amount;
- `ВидОперации` — конфигурируемо, pilot default `REPOST`;
- `СчетДтИсточник`/`СчетКтИсточник` — deterministic source-account trace fields по принятому output adapter;
- `ПравилоДт`/`ПравилоКт` — deterministic rule id (`H79_DEBIT_TRANSFER_V1` / `H79_CREDIT_TRANSFER_V1`);
- `ИдентификаторФинЗаписи` — deterministic id;
- `Содержание` включает run_id, source row ref, исходную организацию/счет/ЦФО/поставщика, document organization, направление и contract version.

Поля, для которых HAT reference или новый сервис не дают доказанного значения, не должны заполняться догадкой: mapping фиксируется отдельным adapter contract и тестом.

## 9. Артефакты запуска

Каждый run создает:

- `input_manifest.json`
- `normalized_balances.jsonl`
- `posting_rows.jsonl`
- `summary.json`
- `run_control.xlsx`
- `export_manifest.json`
- `export/*.xlsx`

Минимальные листы `run_control.xlsx`:

- `Итоги`
- `Параметры_запуска`
- `Остатки_79`
- `Готовые_проводки`
- `Блокировки`
- `Контроль_до_после`
- `Исходные_строки`
- `Проверка_экспорта`

## 10. Обязательные инварианты

- exact account matching only (`79.2`, `79.3`);
- Decimal arithmetic;
- deterministic output and ids;
- no duplicate source row consumption;
- no aggregation that loses source organization/ЦФО/Поставщик РВП traceability;
- all exported workbooks reopen and round-trip to the internal PostingRow model;
- errors in mandatory source identity are BLOCKED, not guessed;
- real XLSX/MXL never committed;
- no live 1C writes;
- Implementation agents may never merge their own PRs. Coordinator may merge a Coordinator-generated PR only after an independent ReviewerRunner PASS on the exact current HEAD and all configured GitHub status/review/protection gates. Protection bypass and admin override are prohibited.
